# چت امن مموت — تحلیل چت مخفی تلگرام و پروتکل پیاده‌سازی‌شده

## ۱) نتیجه بررسی morluto/rea

ریپوی [morluto/rea](https://github.com/morluto/rea) یک ابزار عمومی مهندسی معکوس
(MCP برای تحلیل باینری/APK/جاوااسکریپت با JADX و...) است، نه سورس یا استخراجی از
پروتکل تلگرام. اجرای آن در این پروژه نیازمند باینری تلگرام + JDK و JAR مخصوص JADX-MCP
است. چون کلاینت اندروید تلگرام **متن‌باز** و پروتکل چت مخفی آن **مستند رسمی** دارد،
مسیر تمیزتر و دقیق‌تر، تحلیل مستقیم همان منابع بود — همان کاری که REA برای اپ‌های
بسته انجام می‌دهد، اینجا روی سورس رسمی انجام شد.

## ۲) سیستم چت مخفی تلگرام (شواهد از سورس رسمی)

منبع: `SecretChatHelper.java` در کلاینت متن‌باز تلگرام (DrKLO/Telegram) و مستندات
MTProto (لایه فعلی Secret Chat = 151):

| مکانیس | تلگرام |
|---|---|
| تبادل کلید | Diffie-Hellman روی گروه MODP ‏۲۰۴۸ بیتی؛ توان‌های تصادفی ۲۵۶ بایتی `a`/`b`، اعتبارسنجی `g_a/g_b` (`isGoodGaAndGb`)، کلید نشست `auth_key = g^(ab) mod p` (۲۵۶ بایت) |
| اثر انگشت کلید | `key_fingerprint` = هشت بایت پایانی `SHA1(auth_key)`؛ تصویر/کد مقایسه بصری از `SHA256(auth_key)` |
| رمز پیام | MTProto 2.0: ‏`msg_key` از SHA256 روی بخش‌هایی از auth_key و متن پدشده، استخراج AES-Key/IV با SHA256، رمز **AES-256-IGE**، پدینگ تصادفی تا مضرب ۱۶ |
| ترتیب و ضد تکرار | `DecryptedMessageLayer` با `in_seq_no`/`out_seq_no` (گام ۲) و مذاکره نسخه لایه |
| محرمانگی روبه‌جلو (PFS) | **Rekey**: تبادل DH تازه بعد از **۱۰۰ پیام ارسالی یا ۷ روز** (`requestNewSecretChatKey` هنگام `key_use_count_out >= 100`) با پیام‌های کنترل request/accept/commit و `future_auth_key` مرحله‌ای |
| دامنه | فقط ۱به۱ و **وابسته به همان دستگاه**؛ گروه‌ها در تلگرام سرتاسری نیستند |

نقاط ضعف شناخته‌شده مدل کلاسیک: تبادل DH **بدون احراز هویت** انجام می‌شود (دفاع در
برابر واسطه فعال فقط «مقایسه دستی اثر انگشت» است) و AES-IGE ساختار AEAD مدرن نیست.

## ۳) پروتکل مموت (همان معماری، رمزنگاری مدرن)

پیاده‌سازی در `android/app/src/main/java/ir/mamoot/app/crypto/` — بدون هیچ کتابخانه
خارجی، فقط `java.security`:

| بخش | مموت |
|---|---|
| هویت بلندمدت | زوج‌کلید EC P-256 روی خود گوشی؛ کلید خصوصی فقط داخل خزانه رمز‌شده با Android KeyStore؛ کلید عمومی روی پروفایل منتشر و نزد مخاطب **Pin** می‌شود (TOFU؛ تغییر کلید = هشدار امنیتی) |
| تبادل کلید | ECDH زودگذر P-256 با پیام‌های `k1` (init) و `k2` (accept) — معادل request/accept تلگرام — که کلید زودگذر هر طرف با **کلید هویتش امضا (ECDSA)** می‌شود؛ یعنی برخلاف تلگرام، تبادل از ابتدا احراز‌شده است |
| کلید نشست و اثر انگشت | از راز ECDH با HKDF-SHA256؛ اثر انگشت ۸ بایتی از SHA256 راز مشترک در هر پاکت پیام می‌آید (معادل `key_fingerprint`) و «کد امنیتی» قابل‌مقایسه دستی از ترکیب دو کلید هویت + اثر انگشت نشست ساخته می‌شود |
| زنجیره پیام | برای هر جهت یک زنجیره کلید متقارن؛ هر پیام یک کلید یک‌بارمصرف (HMAC) دارد و زنجیره به جلو می‌چرخد — کلید پیام‌های قبلی قابل بازسازی نیست |
| رمز پیام | **AES-256-GCM (AEAD)** با نانس تصادفی ۹۶ بیتی؛ AAD شامل شناسه گفتگو، فرستنده، اثر انگشت و شماره ترتیب است و از نسخه ۰٫۴ «مرحله پاکت» (`m` پیام / `c` کنترل) هم به AAD گره خورده است تا برچسب پاکت قابل جابه‌جایی نباشد (پاکت‌های قدیمی با AAD قبلی همچنان خوانا می‌مانند) |
| ترتیب/ضدتکرار | شماره ترتیب یکنوا برای هر جهت؛ تکرار رد می‌شود؛ برای تحویل نامرتب کلیدهای جاافتاده نگه داشته می‌شوند، اما از نسخه ۰٫۴ با سقف ۲۵۰ کلید (حذف قدیمی‌ترین‌ها + پاک‌سازی حافظه) و فاصله بیش از ۱۰۰ پیام در هر جهش مستقیم رد می‌شود |
| Rekey | دقیقاً قاعده تلگرام: بعد از **۱۰۰ پیام ارسالی یا ۷ روز** تبادل DH تازه؛ کلید آینده مرحله‌ای فعال می‌شود و دوره قبلی برای پیام‌های در راه مدتی خوانا می‌ماند |
| حمل‌ونقل | پاکت‌های رمز (`MAM1.*`) به‌عنوان متن پیام از همان API معمول رد می‌شوند؛ سرور هرگز کلید یا متن خوانا نمی‌بیند و اعلان‌ها هم متن پیام را نشان نمی‌دهند |
| دامنه | چت خصوصی ۱به۱ و وابسته به دستگاه (مثل تلگرام)؛ گروه‌ها آگاهانه «بدون رمزنگاری سرتاسری» برچسب می‌خورند |

### قالب پاکت‌ها

```
پیام:      MAM1.m.<fingerprint>.<seq>.<nonce>.<ciphertext>
کنترلی:    MAM1.c.<fingerprint>.<seq>.<nonce>.<ciphertext>
شروع تبادل: MAM1.k1.<exchangeId>.<ephemeralPub>.<signature>
پذیرش:     MAM1.k2.<exchangeId>.<ephemeralPub>.<signature>
```

### بار مفید رمز‌شده (داخل ciphertext)

| بایت نوع | معنی |
|---|---|
| `T` | متن ساده |
| `D` | متن با حذف خودکار (TTL) |
| `Q` | پاسخ به پیام دیگر (شناسه هدف + TTL) — از ۰٫۴ |
| `F` | پیام بازارسال‌شده (TTL) — از ۰٫۴ |
| `X` | پایان چت امن (کنترلی) |
| `R` | ویرایش پیام قبلی (کنترلی) |
| `A` | واکنش به پیام (شناسه هدف + ایموجی؛ خالی = حذف واکنش) — از ۰٫۴، کنترلی |

یعنی پاسخ، بازارسال و واکنش در چت امن کاملاً داخل لایه رمز می‌مانند و سرور
از آن‌ها هیچ ابرداده‌ای نمی‌گیرد.

### راستی‌آزمایی و پشتیبان (۰٫۴)

- **شماره امنیتی (Safety Number)**: عدد ۶۰ رقمی به سبک Signal؛ برای هر طرف
  ۵۲۰۰ بار SHA-512 روی «نسخه + کلید عمومی هویت + شناسه کاربر» چرخانده می‌شود و
  دو نیمه ۳۰ رقمی مرتب و چسبانده می‌شوند. روی هر دو گوشی یکسان است و تا وقتی
  کلید هویت عوض نشود ثابت می‌ماند.
- **پشتیبان رمزنگاری‌شده**: کانتینر `MAMOOT-BACKUP-V1` با PBKDF2-HMAC-SHA256
  ‏(۲۱۰٬۰۰۰ دور) + AES-256-GCM؛ شامل کلید هویت، وضعیت نشست‌ها و تاریخچه محلی.
  پشتیبان هر حساب فقط روی همان حساب بازیابی می‌شود و بدون گذرواژه برای هیچ‌کس
  خوانا نیست.
- تبادل کلید نیمه‌کاره بعد از ۳۰ روز منقضی می‌شود و وضعیت زنجیره‌ها به‌صورت
  همگام (commit) ذخیره می‌شود تا با مرگ ناگهانی فرایند، زنجیره به عقب برنگردد.

### محدودیت‌های آگاهانه نسخه ۰٫۱

- چنددستگاهی نیست (مثل چت مخفی تلگرام)؛ نصب دوباره/گوشی تازه = نشست تازه و پیام‌های
  رمز‌شده قبلی روی سرور دیگر خوانا نیستند (متن خوانده‌شده روی همان گوشی، رمز‌شده
  در حافظه محلی می‌ماند).
- تحویل پیام با Polling تطبیقی و Delta-Sync است (بدون FCM و بدون WebSocket دائمی)
  تا روی پلن رایگان و اینترنت ایران کم‌مصرف و پایدار باشد؛ بررسی پس‌زمینه هر ۱۵ دقیقه.
- سقف متن پیام امن ۱۵۰۰ نویسه است (محدودیت طول ستون سرور پس از بست‌بندی رمز).

## ۴) تست‌ها

تست‌های واحد JVM در `android/app/src/test/.../crypto/` در CI اجرا می‌شوند:
توافق ECDH، امضا/جعل تبادل کلید، گفتگوی کامل دوطرفه، تحویل نامرتب و رد Replay،
دستکاری ciphertext، چرخش Rekey و خوانایی پیام درراه دوره قبل، سریال‌سازی وضعیت
زنجیره، رد پاکت با برچسب مرحله جابه‌جاشده (AAD)، سقف کلیدهای جاافتاده و رد فاصله
بیش از حد مجاز، انقضای تبادل نیمه‌کاره، بارهای پاسخ/بازارسال/واکنش، بردار
استاندارد PBKDF2، تقارن و قالب Safety Number و رفت‌وبرگشت/دستکاری پشتیبان رمز‌شده.
